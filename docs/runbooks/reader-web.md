# 독자 웹 런북 (R4)

로그인 없이 누구나 여는 화면입니다. **탐색**(`/`)에서 기술 분야·DX 사업부로 기사를 좁혀 읽고, **기술 레이더**(`/radar`)에서 카테고리·테마·기술의 기간별 흐름과 부상 신호를 봅니다. 분류는 P4(분야 15·테마 75·사업부 6·영향·범위·관련도)를 그대로 씁니다.

## 1. 구조

```
브라우저 ──HTTPS──▶ Caddy(8700) ──▶ web(Next.js) ──내부망 + X-Public-Key──▶ api(/api/public)
                    │  /              : 인증 없음 (탐색·레이더·다이제스트·RSS)
                    │  /console*      : 관리자 매직링크 세션 (P8, ops-console.md §2-1)
                    │  /api/public*   : 외부에서는 항상 404
                    │  /api/admin*    : 외부에서는 항상 404
```

- 독자 API(`/api/public`)는 웹 서버만 호출합니다. 콘솔 키와 다른 `PUBLIC_API_KEY`를 씁니다. 공개 페이지가 콘솔 권한을 갖지 않게 하려는 것입니다.
- `PUBLIC_API_KEY`가 비어 있으면 독자 API는 503을 돌려주고, 독자 화면은 "기사를 불러오지 못했습니다"를 보여 줍니다. 콘솔은 영향을 받지 않습니다.
- 응답은 본문 전문·소스 키·검증 단계·비용 같은 운영 정보를 담지 않습니다. 원문은 링크로만 연결합니다.

## 2. 처음 설정 (1회)

`.env`에 키를 넣고 다시 띄웁니다. 값은 아무 무작위 문자열이면 됩니다.

```bash
echo "PUBLIC_API_KEY=$(openssl rand -hex 24)" >> .env
scripts/dev.sh up
```

로컬 개발에서는 API와 웹에 같은 값을 줍니다.

```bash
PUBLIC_API_KEY=dev-public scripts/dev.sh api-dev
PUBLIC_API_KEY=dev-public scripts/dev.sh web-dev
```

### 3.1 기술 레이더 구성

분류 축은 **카테고리(분야 15) → 테마(75) → 기술(카드 키워드)** 입니다. DX 사업부는 맨 위 분류가 아니라 필터이고, 선택 항목 상세에 "연관 DX 사업부"로만 나옵니다.

| 영역 | 답하는 질문 | 내용 |
|---|---|---|
| 지금 볼 신호 | 무엇부터 봐야 하나 | 규칙으로 뽑은 카드(한 테마는 카드 하나에만): 급상승 테마, 이례적인 날(이번 기간의 카테고리 이상치), 신규 기술(최근 3기간 안 첫 보도), 재등장(공백 뒤 복귀), 연구 선행(논문·OSS ≥50% + 상승), 개발자 반응 선행(반응 비중이 언급 비중의 2배 이상), 상용화 이동(논문·OSS 비중이 기준 기간 대비 20%p 이상, 두 비율 z ≥ 2로 감소), 화제 과열(뉴스·커뮤니티가 평소의 1.5배 이상인데 연구는 평소 수준), 검증 필요(실효 출처 2.5곳 미만이거나 뉴스 중 공식 발표 50% 이상), 국내 공백(해외 4건 이상, 국내 0건), 융합 신호(새 기술 쌍 또는 새 카테고리 교차), 관심 감소 |
| KPI | 전체 규모 | 기사·이슈·출처·연구·오픈소스 비중(8기간 추이), 신규·급상승 기술 수, 상승세 테마 수 |
| 카테고리·테마 지도 | 관심이 어디에 몰렸고 어디가 뜨거워지나 | 트리맵. 면적 = 이번 기간 언급량, 색 = 모멘텀 z (따뜻한 색 상승, 차가운 색 하락) |
| 테마 포지셔닝 | 대응할 것과 선점할 것 | 가로 언급량(로그) × 세로 z. 사분면 주도·부상·정착·잠복. 원 크기 = 출처 수, 색 = 신호 단계 |
| 타이밍 히트맵 | 각 테마가 언제 달아올랐나 | 테마 × 8기간, 행마다 그 테마 최고치 기준으로 칠함 |
| 일별 캘린더 | 언제 무슨 일이 있었나 | 최소 12주의 일별 보도량. 한 카테고리가 같은 요일 평소의 2.5배 이상(8건 이상)이던 날을 테두리로 표시하고 그날 유독 많던 기술을 붙임 |
| 테마 순위 변화 (범프 차트) | 누가 치고 올라오고 누가 밀려나나 | 이번 기간 상위 10개 테마의 기간별 순위. 첫 기간 대비 3계단 이상 움직인 선만 색칠, 상위 10위 밖이던 구간은 선이 끊김 |
| 기술 워드 클라우드 · 부상 기술 워치리스트 | 많이 말해진 기술, 새로 뜨는 기술 | 크기 = 언급량, 색·굵기 = 수명주기(신규·급상승·상승·유지·하락) |
| 반응 vs 보도 | 보도는 적어도 개발자가 먼저 반응하는 곳, 보도만 많고 반응은 없는 곳 | 테마별 언급 비중(가로) × 반응 증가 비중(세로) 산점도, 대각선 위 = 반응이 보도보다 큼. 옆에 반응 급등 항목(스타·포인트 증가량) |
| 지역 관점 | 해외에서 뜨는데 국내는 조용한 것, 국내가 유독 많이 다루는 것 | 테마 × 출처 지역 특화 지수(LQ) 히트맵, 국내 공백 기술, 국내 반영 지연(해외 첫 보도 → 국내 첫 보도 일수) |
| 카테고리 점유율 | 관심의 무게중심 이동 | 카테고리별 Share of Voice 소형 다중 차트(같은 눈금), %p 변화, 기회·위험·관찰 막대 |
| 신호 단계 | 연구 단계인가 시장에 나왔나 | 테마별 트랙 구성(논문·특허, 오픈소스, 커뮤니티, 뉴스). 세로 눈금 = 직전 기간 논문·OSS 비중 |
| 기회·위험 균형 | 어느 테마가 기회로, 어느 테마가 위험으로 읽히나 | 영향 분류 diverging 막대(위험 ← 관찰 → 기회), 순기회 = (기회 − 위험) ÷ 전체 × 100 |
| 확산 경로 | 어느 트랙에서 먼저 나오고 얼마 만에 옮겨가나 | 이슈 묶음과 같은 식별자(arXiv·DOI·저장소·CVE·3GPP·특허·Hugging Face)를 공유하는 보도를 이어 "먼저 → 다음" 트랙 흐름도(Sankey)와 경로별 걸린 시간 중앙값, 식별자 종류별 연결 수 |
| 카테고리 교차 | 어느 분야끼리 만나고 있나 | 한 보도가 두 카테고리 테마에 함께 분류된 수의 행렬, 직전 기간에 없던 교차는 점으로 표시 |
| 기술 융합 네트워크 | 어떤 기술이 함께 이야기되기 시작했나 | 같은 기사에 함께 나온 기술 쌍. 배수 = lift(우연 대비), 보라색 선 = 이번 기간 첫 동시 언급 |
| 선택 항목 (오른쪽, 모바일은 위) | 그 항목의 근거 | 8기간 막대 + 직전 평균선(진행 중 기간은 지금 속도 기준 예상치를 옅게), 실효 출처·공식 발표 비중, 트랙 구성 이번/직전, 영향, 테마, 함께 언급된 기술, 연관 DX 사업부, 지역별 건수와 처음 보도된 순서, 대표 이슈 |

화면 위 구역 바(신호·지도·포지셔닝 …)로 각 차트로 바로 이동합니다. 태블릿 이상에서는 스크롤해도 머리 아래에 붙어 있습니다.
| `/digests`, `/digests/2026-10-04` | 다이제스트 목록과 본문 (모델·비용 정보 없음) |

## 4. 숫자 읽는 법

- **기간:** 탐색의 1일·7일·30일은 지금부터 거꾸로 센 구간, 레이더는 KST 달력 기준(주 = ISO 주, 월요일 시작)입니다.
- **증감:** 직전 같은 길이 기간과 비교한 비율입니다. 직전 기간이 0건이면 "–"(탐색 키워드는 "신규")로 표시합니다.
- **모멘텀 z (레이더):** (이번 기간 − 직전 7기간 평균) ÷ 직전 7기간 표준편차(최소 1). +2σ 이상이면 이례적인 증가입니다.
- **수명주기 (레이더):** 신규 = 직전 7기간에 없다가 2건 이상·출처 2곳 이상 / 급상승 = z ≥ 2이고 평균의 1.5배 이상·출처 2곳 이상 / 상승 = 평균의 1.3배 이상 / 하락 = 평균 2건 이상인데 70% 이하 / 나머지 2건 이상은 유지.
- **진행 중 기간 (STAT-2):** 이번 주·달은 직전 기간들도 같은 시점까지만 세어 비교합니다. 같은 경과 비율을 쓰므로 주는 같은 요일·시각, 달은 길이에 맞춘 같은 비율입니다. 변화율·z·상태와 트랙 구성(이번/직전/기준)이 이 값을 쓰고, 응답의 `paced`에 담깁니다. 막대 차트는 전체 건수 그대로입니다. "새로 등장"은 같은 시점 이후라도 직전 기간에 한 번이라도 나왔으면 붙이지 않습니다.
  - 데모 코퍼스 측정(W40 진행 중, 테마 26개 중 하락): 월요일 09시 25 → 0, 화요일 18시 22 → 6, 목요일 15시 16 → 7. 보정 전에는 주 초반에 "관심 감소"가 쏠렸습니다.
- **기술(키워드):** 카드 키워드를 소문자로 바꾸고 공백·하이픈·밑줄·가운뎃점을 지운 뒤 별칭 표(`apps/api/src/news_insight/public/keywords.py`의 `ALIASES`)로 동의어·번역어를 묶습니다("AI 에이전트" = "AI-Agent", "대형언어모델" = "LLM"). 같은 기술이 둘로 쪼개져 보이면 별칭 표에 한 줄 추가하세요. 탐색 화면 키워드도 같은 규칙을 씁니다. 표시 이름은 가장 많이 쓴 표기, 8기간 합 2건 이상만 집계합니다.
- **첫 등장·재등장:** 필터를 건 채로 전체 기간에서 그 기술의 첫 보도 시각을 찾습니다. 최근 3기간 안이면 "첫 등장", 직전 7기간에 없다가 나왔는데 그 전에 보도된 적이 있으면 "재등장"입니다.
- **반응:** 지표 스냅샷(스타·포인트·좋아요·댓글 등)이 이번 기간에 늘어난 양. 항목마다 log(1+증가량)을 지표별로 더해 테마에 합산합니다. 조회수처럼 늘기만 하는 값은 쓰지 않습니다.
- **이례적인 날:** 카테고리별로 같은 요일의 직전 4주 평균과 비교해 z ≥ 3, 2.5배 이상, 8건 이상인 날. 전체 합계로 보면 한 분야의 행사가 희석되고 주말이 과민해져서 카테고리 단위로 봅니다.
- **테마 다중 집계:** 한 기사가 테마 여러 개에 걸치면 각 테마에 한 번씩 셉니다. 카테고리는 기사당 하나라 점유율 합이 100%입니다.
- **신호 단계:** 논문·오픈소스 비중 50% 이상 = 연구 주도, 20~50% = 확산, 20% 미만 = 시장 주도. 소스 구성의 영향을 받으니 같은 테마의 변화(%p)를 주로 보세요. 비교 기준은 직전 1기간이 아니라 기준 기간(직전 7기간) 합계입니다. 한 주 단위 소량 건수는 흔들림이 커서입니다.
- **실효 출처 수:** 1 ÷ HHI(출처별 기사 비중 제곱합). 5곳이 똑같이 썼으면 5, 한 곳이 대부분이면 1에 가깝습니다. 출처 수보다 쏠림을 잘 보여 줍니다.
- **공식 발표 비중:** 카탈로그 `category: official_vendor` 출처(기업 뉴스룸 등)의 비중. 높으면 기업 발표가 끌고 가는 주제입니다.
- **지역 특화 지수(LQ):** (그 지역 보도 중 테마 비중) ÷ (전체 보도 중 테마 비중). 2 = 두 배 더 다룸, 0.5 = 절반. 그 지역에서 기대되는 건수가 1.5건 미만이면 판단하지 않고 회색으로 둡니다.
- **국내 반영 지연:** 신규·급상승 기술만, 직전 7기간 범위 안에서 해외 어느 지역의 첫 보도 → 국내 첫 보도까지의 일수입니다.
- **확산 경로:** 이번 기간 안에 새 트랙에 처음 도달한 연결만 셉니다. 같은 시각이면 논문 → 오픈소스 → 커뮤니티 → 뉴스 순으로 봅니다. 수집 주기가 트랙마다 달라(논문·OSS는 수 시간~하루) 몇 시간 단위 차이는 수집 지연일 수 있습니다.
- **진행 중 예상치:** 이번 기간 건수 ÷ 경과 비율. 기간의 15% 이상 지났을 때만 표시합니다.
- **이슈:** P4 묶음 단위입니다. 묶이지 않은 기사는 그 자체로 하나의 이슈로 셉니다.
- **공개 대상:** 카드가 만들어지고 현재 분류 리비전으로 분류된 기사입니다. V6 전 Canary 소스의 기사도 포함합니다.

| 모든 독자 화면이 "불러오지 못했습니다" | web·api 양쪽에 같은 `PUBLIC_API_KEY`가 들어 있는지. API 로그에 401이면 값 불일치, 503이면 api 쪽 미설정 |
| 탐색은 되는데 다이제스트 띠가 없음 | 아직 발행된 다이제스트가 없거나, 최신 다이제스트를 읽다 오류가 났습니다(웹 로그에 `latest digest failed`). 피드는 계속 보입니다 |
| 필터를 골라도 0건 | 범위가 "DX 관련 + 의존 기술"이면 `excluded`·`irrelevant` 분류는 빠집니다. 범위를 "전체"로 바꿔 보세요 |
| 레이더 지도가 대부분 비어 있음 | 카드가 아직 현재 `TAXONOMY_REVISION`으로 분류되지 않았습니다. `docs/runbooks/stories-classification.md`의 재분류 절차를 확인하세요 |

## 데일리 브리핑 (P8)

| 경로 | 내용 |
|---|---|
| `/briefings` | 가장 최근에 **발행된** 브리핑. 왼쪽(모바일은 "브리핑" 탭)에 헤드라인·개요·핵심 인사이트와 4개 트랙 선정 기사, 오른쪽("인사이트" 탭)에 페르소나 통찰(경영진·사업부장·도메인), 전략 요약, 근거 지도(많이 인용된 기사), 로드맵 시사점(1·3·5년), 시장 영향도(사업부별 기회·위험·관찰), 지난 브리핑 |
| `/briefings/YYYY-MM-DD` | 그날 발행본. 이전·다음 이동, 없는 날짜는 404 |

- 독자 API: `GET /api/public/briefings`(목록), `/briefings/latest`, `/briefings/{date}`. 게이트에서 막힌(blocked) 버전과 게이트 상세·비용·오류는 내보내지 않습니다.
- 기사 행은 탐색 피드와 같은 `StoryRow`라서 누르면 기사 상세 시트가 열립니다.
- E2E: `scripts/dev.sh web-e2e`. `news_insight_e2e` DB에 오늘·어제 브리핑 고정 데이터를 넣고 API(8712)·웹(8713)을 띄워 시스템 Chrome으로 검사합니다(관리자 로그인 가드 포함). 실제 DB는 건드리지 않습니다.

## 7. 레이더 데모 데이터

차트가 제 역할을 하는지 보려고 패턴을 심은 합성 데이터를 만들 수 있습니다. 이름에 `demo`가 들어간 데이터베이스에만 씁니다(운영 DB 보호).

```bash
psql -h localhost -p 8720 -U news -d postgres -c "CREATE DATABASE news_insight_demo"
cd apps/api
export DATABASE_URL=postgresql+psycopg://news:news-dev-password@localhost:8720/news_insight_demo
uv run alembic upgrade head && uv run python scripts/radar_demo_seed.py
PUBLIC_API_KEY=dev-public uv run uvicorn news_insight.main:app --port 8711   # 웹은 같은 키로 web-dev
```

약 40주, 7천 건, 지표 스냅샷 7만여 건이 생기고 심어 둔 패턴(급상승·첫 등장·재등장·연구 선행·상용화 이동·화제 과열·공식 발표 쏠림·국내 공백/지연·논문→저장소→커뮤니티→뉴스 연결·개발자 반응·행사일·카테고리 교차·별칭)은 스크립트 첫머리에 적혀 있습니다. 레이더가 이 패턴을 못 찾거나 없는 패턴을 만들어 내면 규칙을 의심하세요. 데이터를 다시 만들면 웹 캐시(최대 10분) 때문에 `.next`를 지우고 다시 띄워야 바로 보입니다.

### 신호 회귀 테스트 (QA-1)

`scripts/dev.sh radar-qa`가 같은 데모 데이터를 고정 시각(`RADAR_DEMO_NOW=2026-10-04T15:00:00+00:00`)으로 `news_insight_qa_demo`에 만들고, `scripts/radar_qa_export.py`로 끝난 기간 네 개(2026-W39, W40, 2026-09, 2026-Q3)의 레이더 응답을 JSON으로 내보낸 뒤 `apps/web/tests/radar-qa.test.ts`를 돌립니다. CI에서도 매번 실행합니다(약 1분).

- 검사 대상은 "심어 둔 패턴이 해당 규칙의 후보에 드는가"입니다(`radarSignals(radar, candidates)`가 규칙별 후보를 순위 매기기 전에 모읍니다). 1등 카드가 무엇인지는 보지 않으므로 시드의 난수 순서가 바뀌어도 깨지지 않습니다.
- 실패하면: 규칙이나 통계(z, 상태, 점유율)를 바꿔서 패턴을 놓친 것인지, 시드를 바꿔서 패턴이 약해진 것인지 먼저 가립니다. 시드를 고쳤다면 패턴 강도(기본량, 이벤트 요일, 키워드 가중치)를 올려 표본 크기 문턱을 넉넉히 넘기게 합니다. 주말 이벤트는 물량이 0.45배라 패턴이 약해집니다.
- 새 규칙이나 패턴을 넣으면 시드 첫머리의 패턴 목록과 테스트의 `PLANTED` 표를 함께 고칩니다.

## 레이더 캐시와 보정 지표 (2026-10-05, plan 08 B6·B7)

- **응답 캐시:**
  - API가 레이더(`/radar`, `/radar/topic`) 응답을 Redis에 저장합니다. 끝난 기간은 24시간, 진행 중인 기간은 15분 보관합니다.
  - 키는 해석된 보기(기간, 범위, 필터)에 앱 버전과 체계 리비전을 더해 만듭니다. 그래서 배포나 체계 개정 뒤에는 자연히 새 키를 씁니다.
  - 응답 헤더 `X-Cache: hit|miss`로 확인합니다. 운영(compose)에서만 켜지고(`RADAR_CACHE=true`), 테스트와 호스트 개발 서버에서는 꺼집니다.
- **예열:** Celery `radar.warm`이 10분마다 기본 보기를 미리 계산합니다. 기본 보기는 주·월·분기 × 현재·직전 기간 × 범위(DX 관련·전체)입니다. 필터를 건 보기는 첫 요청 때 계산해 같은 규칙으로 저장합니다.
- **보정 지표 (STAT-1):** 레이더 항목에 두 값이 추가됐습니다.
  - `capped`: 출처 하나가 하루에 같은 주제로 기여하는 건수를 3건까지만 셉니다.
  - `normalized_share`: 트랙(뉴스·논문·OSS·커뮤니티)마다 그 주제가 차지하는 비중을 구해 평균한 값(%)입니다. 소스를 추가하거나 퇴역시켜도 크게 흔들리지 않습니다.
  - 기간별 활성 소스 수는 KPI의 `sources`에 있습니다.

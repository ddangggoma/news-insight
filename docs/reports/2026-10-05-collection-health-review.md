# 전체 수집처 크롤링·수집 동작 점검

기준: 2026-10-05 14:45:54 KST 운영 DB 스냅샷. 후속 단발 재검사는 같은 세션에서 배포 API 컨테이너의 SafeFetcher로 수행.

## 결론

**전체 수집처가 이슈 없이 동작하고 있지는 않다.** 수집 엔진과 스케줄러는 작동 중이고 실행된 요청의 성공률도 높지만, 검증 미통과로 시작되지 않은 122개, 일시정지 32개, 최근 요청 실패 상태 17개가 있다. 정상 요청 결과라도 데이터 추출·최신성·목적 적합성이 보장되지 않는다.

운영 DB 1,309개를 전수 조회했다. 이 중 retired 36개를 제외한 현 카탈로그 범위는 1,273개다. 기존 등록을 변경하거나 재수집 작업을 발행하지 않았으며, 조사 중 DB는 읽기 전용 트랜잭션을 사용했다.

## 1. 전체 상태

| 구분 | 개수 | 의미 |
|---|---:|---|
| 수집 이력 있음·현재 연속 실패 없음 | 1,102 | 정상 가동의 긍정적 지표. 콘텐츠 품질 검증 완료를 뜻하지 않음 |
| 수집 대상이나 최근 요청 실패 | 17 | 모두 OpenAlex 429, 각 연속 실패 1회. 과거 성공 이력 있음 |
| 검증 미통과·수집 미시작 | 122 | 수집 실행 자체가 없으므로 요청 성공률 통계에 드러나지 않음 |
| 일시정지 | 32 | 기술 문제 16개 + 낮은 관련도 판정 16개 |
| retired | 36 | 운영 대상에서 제외된 기존 OSS 항목. 장애로 세지 않음 |
| 합계 | 1,309 | 카탈로그 1,273 + retired 36 |

현 카탈로그의 1,102개(86.6%)에 수집 이력이 있고 현재 연속 실패가 없다. 171개(13.4%)는 실패·정지·미시작 상태다. 이 둘은 채널 운영 분류이며 모든 기사 정확도나 누락률의 지표가 아니다.

수집 가능 대상으로 분류된 1,119개에는 런타임 누락, 성공 이력 없음, 장기 성공 단절, 장기 배정 지연이 발견되지 않았다. 장기 단절은 `max(24시간, 수집주기×2)`, 장기 배정 지연은 `max(1시간, 수집주기×2)`로 점검했다. 수분 단위 지연이 전혀 없다는 의미는 아니다.

## 2. 최근 실행 기록

최근 24시간:

| 결과 | 횟수 |
|---|---:|
| success | 25,131 |
| not_modified | 8,226 |
| failed + dead_lettered | 204 |
| 로컬 도메인 예산에 따른 skipped | 1,461 |

실제 시도된 요청 기준 `(success + not_modified) / (success + not_modified + errors)`는 **99.39%**다. not_modified는 새 항목 수집 성공과 구분되지만 정상 통신 결과에 포함했다. skipped는 외부 요청 실패가 아니라 내부 속도 제한에 의한 연기이므로 분모에서 제외했다.

최근 1시간은 success 1,060, not_modified 343, failed 3, skipped 122다. 최근 24시간 오류가 있었지만 현재 연속 실패가 해소된 채널도 80개다. 과거 오류를 전부 현재 장애로 계산하지 않았다.

24시간 오류의 원인: rate_limited 79, timeout 41, HTTP 403 31, HTTP 400 17, server_error 16, blocked_mime 10, transport 9, blocked_too_large 1. 미해결 DLQ는 **23건, 21개 소스**다. DLQ가 남아 있어도 현재 복구되었을 수 있으므로 최신 실행 상태와 함께 봐야 한다.

worker·API 등 주요 컨테이너는 healthy, scheduler는 실행 중이다. 최근 20분 로그(컨테이너별 최대 8,000줄)에서 구조화 로그의 ERROR/CRITICAL은 발견되지 않았다. 이는 외부 소스 오류가 없다는 뜻이 아니다. 소스 실패는 fetch_runs에 기록되고 Celery 작업 자체는 정상 반환할 수 있다.

## 3. 수집이 시작되지 않은 122개

| 원인 | 개수 | 판단·제안 |
|---|---:|---|
| NAVER_CLIENT_ID 인증정보 미설정 | 50 | 자격증명 제공·권한 확인 후 검증. 인증 비밀값은 조회·출력하지 않음 |
| 검증 중 HTTP 429 | 47 | 제공자별 공통 예산·동시성·재시도 간격 점검. 키/요금/요청 제한 원인은 추가 확인 필요 |
| robots 접근 불허 | 18 | 정상적인 정책 차단. 우회하거나 단순 장애 재시도로 해결할 대상 아님 |
| robots 조회 실패 | 3 | 삼성 KR·Global 타임아웃, NAVER D2 scheme 오류 |
| 최근 완전한 표본 부족 | 4 | Arch Linux, HN MediaTek, Spotify Engineering, StackOverflow ONNX. 저빈도와 파서 문제 구분 |

자동 검증은 코드상 10분마다 배치 실행하지만 실패 후보는 마지막 실패 후 24시간 대기한다. 외부 문제가 회복되어도 즉시 재개되지 않을 수 있다. 검증 재시도 자체가 상태를 변경하므로 이번 점검에서는 실행하지 않았다.

robots 불허 사례에는 Hacker News RSS, Lobsters RSS, The Register 계열, Science·PNAS 피드 등이 있다. 'URL을 열 수 있다'와 '현재 프로젝트 정책으로 수집할 수 있다'는 다른 상태다. HN은 앞선 검토에서 확인한 공식 API 대안을 검토하는 것이 적합하다.

## 4. 현재 진행 중인 오류와 일시정지

### OpenAlex 17개

온디바이스 음성인식·양자점 디스플레이·엣지 AI·고체전지 등 17개 연구 검색 채널의 최근 요청이 429다. 모두 1회 연속 실패로, 영구 중단 판정은 이르다. 같은 제공자의 검색 채널을 소스별로 독립 운영하면 호출 예산을 공유한다는 사실을 놓치기 쉽다.

제안: provider 단위 rate limit·Retry-After·키 한도·일일 예산을 확인하고, 검색식을 통합하거나 시차를 둔다. 이번에는 추가 OpenAlex 요청을 보내 제한을 더 소모하지 않았다.

### 기술 문제로 일시정지 16개

Ericsson, Euractiv, Huawei Central, Pew Internet, PhoneArena, Automotive World의 HTTP 차단, Nature 계열 등의 HTML 반환, TMTPost의 반복 서버 오류, Tom’s Guide 응답 크기 제한 등이 포함된다. 전체 이름·사유는 attention-sources.csv에 있다.

### 품질 정책으로 일시정지 16개

아주경제·조선비즈·이데일리·뉴스1·뉴스시스·뽐뿌·퀘이사존 등이다. 수집기 고장이 아니라 DX 관련도 자동 판정으로 멈춘 경우다. 분류 오류·사이트 전체 수집·관측 기간 부족 가능성을 함께 검토해야 한다. 단순 resume만 하면 같은 사유로 다시 정지할 수 있다.

## 5. 운영 환경에서 단발 재검사한 결과

현재 배포 API 컨테이너에서 프로젝트의 실제 User-Agent, SafeFetcher, MIME·응답 크기 제한을 적용했다. 카탈로그 승격·수집 저장·스케줄 변경은 하지 않았다.

| 대상 | 단발 결과 | 해석 |
|---|---|---|
| Ericsson Blog | 403 재현 | 접근 문제 지속 |
| PhoneArena | 403 재현 | 접근 문제 지속 |
| Nature Electronics | HTML MIME 재현 | RSS 기대와 실제 응답 불일치 |
| Tom’s Guide | 5,242,880바이트 상한 초과 재현 | 큰 응답에 의한 차단 지속. 무작정 전역 상한 확대보다 작은 피드 대안 우선 |
| Samsung KR RSS | 200·20개 파싱, 파서 경고 없음 | RSS 본체는 작동 |
| Samsung robots.txt | timeout 재현 | 정책 검증 경로는 여전히 불안정 |
| TMTPost | 200·16개 파싱, 파서 경고 없음 | 일시 회복 가능. DB의 paused 상태는 유지 |
| Stack Exchange Electronics | 200 JSON | 과거 400이 현재 재현되지 않음. 연속 수집·쿼터 검증은 별도 |

**이전 제안서와의 차이:** 앞선 호스트 요청에서는 삼성 robots.txt가 200이었다. 이번 운영 컨테이너에서는 다시 타임아웃됐다. 따라서 삼성은 '복구 완료'가 아니라 **실행 환경별 경로 불안정으로 재검증 필요**다. 일회성 성공을 지속 가동의 증거로 삼지 않는다.

## 6. 성공 응답인데 실제 데이터가 올바른가

수집 이력과 현재 실패가 없는 1,102개 중 **26개는 최근 24시간 success가 반복되지만 items_seen 합계가 0**이다. Bosch, Boston Dynamics, Intel, CMU, EPFL, MIT CSAIL 등 웹 채널이 포함된다.

코드에서 웹 수집은 알려진 URL·오래된 글·날짜 없는 페이지 등을 제외한 뒤 items_seen을 기록한다. 따라서 0은 '새 글 없음'일 수도 있고, '발견했지만 추출·날짜·robots 단계에서 모두 제외'일 수도 있다. 지금 지표만으로 26개를 장애로 확정하지 않았으며 전부 정상으로도 판정하지 않았다.

추가로 확인된 관측 한계:

- 웹 보강 단계는 일부 페이지 FetchError를 잡고 계속 진행한다. 상위 수집 실행이 success여도 하위 원문 접근 실패가 숨을 수 있다.
- SitemapCollector·자동 크롤러는 complete() 결과만 반환하며, 탈락 단계별 수치를 세분화해서 기록하지 않는다. items_incomplete가 낮다고 모든 페이지가 정상 파싱됐다는 뜻은 아니다.
- 사이트맵 lastmod가 published_at으로 들어갈 수 있어, 수정된 제품 문서가 새 기사처럼 보일 수 있다.
- 사이트맵 자식 목록은 최대 2개만 읽는다. 사이트 전체 수집의 완전성을 보장하지 않으며, 자식 선택과 실제 뉴스 위치가 다르면 새 글을 놓칠 수 있다.
- 알려진 URL은 웹 수집에서 다시 읽지 않는다. 같은 URL의 정정·기술 문서 업데이트를 추적해야 하는 용도와 맞는지 별도 결정이 필요하다.

앞선 14:24 스냅샷에서 전체 수집의 53.8%가 사이트맵, 37.9%가 30일 초과 과거 항목이었다. 이는 이번 14:45 실행 성공률과 다른 시각·집계의 **내용 품질 증거**다. 현재 필터가 개선됐더라도 과거 데이터가 이미 존재하므로 수집 성공 여부와 구분해 관리해야 한다.

제안 지표: discovered / known_skipped / archive_skipped / robots_denied / detail_fetch_failed / missing_date / parsed / ingested. 26개는 이 지표와 사이트의 최신 공지 표본을 대조한 뒤 정상 무변경인지 추출 누락인지 확정하는 것이 필요하다.

## 7. 수정 우선순위 제안

1. **시작되지 못한 핵심 채널:** 삼성의 컨테이너 네트워크·타임아웃, NAVER 인증 설정, 429 제공자 예산 확인.
2. **지속 장애가 재현된 채널:** 403·잘못된 RSS·대용량 피드를 경로 교체 또는 출처별 설정으로 해결. robots 불허는 우회하지 않고 공식 API/허용 경로로 전환.
3. **일시 회복 채널:** TMTPost 등은 제한된 재검증 후 재개 여부 판단. DLQ는 최신 실행 결과와 맞춰 정리.
4. **조용한 누락 탐지:** 26개 0건 채널과 하위 페이지 오류의 단계별 지표 추가.
5. **내용 품질:** 기사/목록/제품 DB 구분, 실제 발행일, 중복·정정 추적, 핵심 출처의 카드 처리량 보장.

수집 상태에는 최소한 `정상 수집 / 정상 변경 없음 / 검증 차단 / 일시 오류 / 정책 정지 / 추출 확인 필요`를 구분해야 한다. 현재 하나의 높은 성공률만으로 전체가 정상이라고 표시해서는 안 된다.

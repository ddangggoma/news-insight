# 수집처 신뢰성·적정성 검토 계획
Created: 2026-10-05

목표는 전체 데이터가 특정 출처·업체·기술에 치우치는지, 수집처의 신뢰성과 인지도는 어떤지, 기술·테마별 OSS 동향과 주요 인물·업체의 움직임을 충분히 포착하는지 검토하는 것이다. 수집처별 유지·제한·통합·교체·중단·보완 제안을 근거와 함께 정리한다. 이번 산출물은 검토 계획이며, 실제 외부 출처 검증과 운영 변경은 후속 작업이다.

## 사용자 의견을 반영한 핵심 질문

1. 전체 데이터와 최종 브리핑이 한두 매체·플랫폼·업체·기술·지역에 과도하게 의존하는가?
2. 수집처가 신뢰할 만한가? 업계 인지도와 해당 기술 분야의 전문성은 어느 정도인가?
3. 기술·테마별로 어떤 오픈소스 프로젝트가 성장·쇠퇴하고 있으며, 그 변화의 근거를 볼 수 있는가?
4. X·Reddit을 포함한 SNS·커뮤니티와 기술계 주요 인물의 발언을 실제로 수집하는가? 무엇이 빠져 있는가?
5. 주요 업체의 기술·제품·연구·사업 동향을 공식 발표와 외부 평가를 함께 보며 추적할 수 있는가?

이 다섯 질문은 모두 최종 보고서의 필수 답변 항목이다. 기존의 수집 안정성·이용조건 점검은 이를 뒷받침하는 공통 검토로 유지한다.

## 추가 분석 설계: 편중·인지도·OSS·인물·업체

### A. 전체 데이터의 편중

- **등록 채널 → 실제 수집 → 고유 콘텐츠 → 카드 → 최종 노출·브리핑** 단계별로 같은 분포를 비교한다. 단계마다 분모·기간·미분류 비율을 명시한다.
- 출처·발행기관·기업집단, 원문 플랫폼, 지역·언어, 기술·테마, 업체, 신호 유형별 비중을 계산한다. 기술×출처, 기술×업체 교차표도 만든다.
- 상위 1·5·10개 점유율과 HHI(점유율 제곱합)를 기록한다. 동일 기업집단·재전재·검색 API 중복을 합친 전후 결과를 비교한다. 플랫폼 도메인을 독립 언론사로 세지 않는다.
- 가장 많은 발행자 또는 업체를 제외했을 때 기술별 순위가 얼마나 바뀌는지 민감도를 확인한다. 현 레이더의 소스별 일일 상한·트랙 정규화가 원출처 집중까지 완화하는지도 확인한다.
- 높은 비중만으로 부적정 판정을 내리지 않는다. 실제 산업 이벤트 집중, 수집 설정 편향, 분류 오류를 구분하고, DX 목적에 따른 목표 범위와 비교해 과잉·공백을 설명한다. 모든 기술을 같은 비율로 맞추지 않는다.

**산출물:** 단계별 편중표, 기술·테마 커버리지 지도, 주요 의존 출처와 누락 영역, 조정 전후 순위 비교.

### B. 신뢰성·인지도·전문성의 분리 평가

- 신뢰성은 정체성·원자료·정정·광고 표시·표본 정확성으로 평가한다.
- 인지도는 `국제적 / 지역·산업 내 / 전문 커뮤니티 내 / 확인 부족`으로 기록하며, 독립 매체·학회·표준기구 등의 인용·참조 근거와 확인일을 붙인다. 팔로워·방문량은 보조 자료로만 사용한다.
- 전문성은 실제 취재·연구·개발 실적과 기술별 심층 정보 기여로 평가한다. 일반 대중 인지도가 낮은 전문 출처도 보완 가치가 있으면 유지한다.
- 유명 기업의 공식 주장, 유명 인물의 의견, 독립적으로 확인된 사실을 표시상 구분한다. 인지도를 사실 정확도의 대체 점수로 쓰지 않는다.

**산출물:** 수집처별 소개·인지도 근거·전문 기술·신뢰성·용도·한계가 함께 있는 출처 평가표.

### C. 기술·테마별 OSS 프로젝트 트렌드

- 저장소의 안정적 식별자와 소유자·이름 변경 이력을 기준으로 프로젝트를 통합한다. 여러 검색식에 반복 등장한 저장소와 릴리스 건수를 분리한다.
- 프로젝트를 기술·테마에 연결하고 복수 테마 중복 집계 방식을 명시한다. 대표 표본으로 설명문·README·프로젝트 목적과 분류 결과를 대조한다.
- **관심 증가:** 7일·30일 stars·forks 순증, 증가율, 직전 기간 대비 가속. 작은 분모의 증가율과 대형 프로젝트의 절대 증가량을 함께 표시한다.
- **개발 지속성:** 최근 릴리스, 기여자 변화, 이슈·PR 응답·처리, 유지관리 상태를 검토한다. 현재 수집되지 않는 지표는 추가 요구사항으로 명시한다. open_issues 개수만으로 건강성을 판정하지 않는다.
- **활용·성숙도:** 라이선스, 문서·설치 예제, 배포·패키지 사용 지표, 실제 도입 근거, 보안 공지를 확인 가능한 범위에서 비교한다. 공개 저장소가 곧 오픈소스 라이선스 프로젝트인지도 확인한다.
- `급상승 / 꾸준한 성장 / 신규 관찰 / 정체·유지관리 주의`를 나누고 대표 프로젝트, 변화량, 변화 이유, 원문 링크를 기술·테마별로 제시한다. 별 증가를 기술 성능이나 채택 증가로 단정하지 않는다.
- stars 정렬 상위 50개·최근 push 조건 등의 검색 설정이 작은 신규 프로젝트나 안정적 성숙 프로젝트를 누락하는지 점검한다. 처음 발견한 높은 stars를 신규 증가로 세지 않는다.
- 관측 시작·끝과 실제 길이를 표시하고 7일·30일 기준점이 부족하면 해당 기간 추세를 보류한다. 검색 순위 밖으로 빠진 프로젝트의 관측 누락, 오래된 마지막 스냅샷도 점검한다. GitHub의 pushed_at을 프로젝트 최초 공개일로 쓰지 않는다.

**산출물:** 기술·테마 → 대표 프로젝트·성장 지표·성숙도·근거의 트렌드 표, 현행 기능과 추가 수집·분석·화면 요구사항의 차이표. 실제 기능 개발은 이 검토에 포함하지 않는다.

### D. SNS·Reddit·주요 인물의 수집 범위

- X·Reddit·Bluesky·Mastodon 등 플랫폼별로 `미등록 / 등록 / 접근 확인 / 최근 원문 수집 성공 / 분석 반영` 상태를 구분한다. 간접 기사 인용을 직접 계정 수집으로 세지 않는다.
- 기술별로 연구자, 핵심 개발자·메인테이너, 기술 책임자, 창업자, 독립 분석가를 선정한다. 현재 역할·실적·공식 계정 연결을 확인하고 특정 기업·영어권·유명 CEO에만 집중되지 않게 한다.
- 인물대장에 이름·소속·전문 기술·선정 근거·공식 계정·대체 블로그·최근 성공 시각을 기록한다. 개인적 일상과 기술적 발언을 구분한다.
- Reddit은 주제별 커뮤니티, 유지관리자의 공식 공지, AMA 및 실제 경험담의 수집 여부를 확인한다. 익명 사용자의 인물을 추정하지 않고 원문·댓글 문맥·공식 계정 확인 수준을 보존한다.
- 개인 의견·예측·자사 홍보·공식 발표·실증 결과를 분리하고 재게시·봇·인용 중복을 확인한다. 반응량을 진실성으로 쓰지 않는다.
- 추가 수집 경로는 실행 시점의 공식 API·이용조건·접근 범위·비용·갱신 주기를 확인해 비교한다. 접근 불가 항목은 RSS·개인 블로그 등 대체 경로와 공백을 명시한다.

**산출물:** 플랫폼×기술×인물 커버리지 표, 핵심 계정·커뮤니티 대장, 누락 및 보완 제안. X·Reddit 추가가 확정되었다고 전제하지 않는다.

### E. 업체별 기술·사업 정보

- 기술·테마별로 주요 업체, 경쟁사, 전문 업체·스타트업을 선정하고 모회사·자회사·브랜드를 연결한다. 고정된 대기업 목록만으로 커버리지를 판단하지 않는다.
- 업체별 뉴스룸, 연구·개발 블로그, 제품·릴리스 문서, 보안 공지, IR·공시, OSS 조직, 주요 인물 계정을 대조한다.
- 기술·제품 출시, 연구 성과, 표준 참여, 특허, 제휴·인수, 투자·실적, 공급망·보안 이슈를 신호 유형별로 정리한다. IR·재무 정보는 기술 전략에 필요한 범위로 다룬다.
- 공식 발표와 독립 보도·실험·고객 경험을 연결해 확인 수준을 표시한다. 업체 홍보량이 산업 내 중요도로 바로 해석되지 않도록 비교한다.
- 업체명·브랜드·약칭의 식별 정확도와 기술·프로젝트·인물 연결 여부를 확인한다. 기사에 회사가 단순 언급된 것과 해당 회사의 주요 사건을 구분한다.

**산출물:** 업체×기술·테마×정보 유형 커버리지 표, 업체별 주요 변화·연결 프로젝트·인물·출처, 정보 공백과 보완안.

## 2. 평가 원칙

- **발행자 → 수집 채널·쿼리 → 개별 콘텐츠**를 구분한다. 동일 발행자의 여러 피드와 같은 기사를 반환하는 여러 검색식을 독립 근거로 세지 않는다.
- **내용의 신뢰성, 목적 적합성, 수집 안정성, 이용조건**을 별도 축으로 기록한다. 높은 가동률이나 관련도로 낮은 신뢰성·미확인 이용조건을 상쇄하지 않는다.
- 공식 발표는 발표 사실의 1차 근거지만 성능·시장 우위 주장까지 독립적으로 입증하지 않는다. 커뮤니티는 탐색 신호, 논문은 심사·철회 상태, 특허는 출원·공개·등록 상태, OSS는 유지관리·실제 사용 근거를 따로 확인한다.
- 출처의 역할은 `사실 근거 / 해석·분석 / 탐색 신호`로 표시한다. 탐색 가치가 높은 소스를 근거 부족만으로 일괄 삭제하지 않는다.
- 기술·테마 및 DX 범위는 실행 시점의 `apps/api/src/news_insight/taxonomy/catalog.py`를 기준으로 삼는다. 자동 분류는 원문 표본과 대조한다.
- 확인된 사실, 판단, 미확인을 구분하고 증거 URL·확인일·표본 수·검토자를 남긴다. 미확인을 최하점이나 통과로 치환하지 않는다.

## 3. 순서와 산출물

### 1단계 — 전체 목록과 운영 상태 대조

카탈로그와 읽기 전용 DB 조회로 등록 상태, V단계, 최근 성공 시각, 최근 7일·30일 수집량 및 발행 사용량을 대조한다. 카탈로그에만 있는 항목과 DB에만 남은 항목을 구분한다.

발행기관·운영 주체, 플랫폼, 원문 도메인, 계정, 채널·검색식을 연결해 출처 계보를 만든다. API 운영자가 원문 저자·발행자와 혼동되지 않는지 점검한다. 같은 기업집단과 보도자료 재전송 관계도 표시한다.

**산출물:** 전체 수집처 검토대장, 중복·계열 그룹, 현재 상태 스냅샷. 비밀키·인증 헤더는 추출하지 않는다.

### 2단계 — 전수 사전 점검과 심층 검토 우선순위

전 항목의 URL·운영자·이용조건 기록·수집 상태·중복 여부를 점검한 뒤 다음 순서로 심층 검토한다.

1. 현재 브리핑·독자 화면에 사용되는 소스와 카드 처리량 누적 80%를 차지하는 소스.
2. 사이트맵·크롤러, 오래된 페이지·목록 페이지 비중이 큰 소스, 겹치는 API 검색식.
3. 자동 정책 통과 또는 이용조건 근거가 부족한 소스, 원발행자·계정 소유자가 불명확한 소스.
4. 나머지 소스와 기술·지역의 공백을 채우는 저빈도 전문 소스.

오늘 운영 보고서에 기록된 FreeBSD·Zigbee2MQTT 등의 사이트맵과 HN·Europe PMC 검색식은 우선 재측정 대상으로 삼는다. 개별 매체의 신뢰성 결론으로 사용하지 않는다.

**산출물:** 우선순위·선정 이유·표본 계획. 처리량 80%는 검토 효율을 위한 기준이며, 나머지 항목도 최종 대장에서 빠지지 않는다.

### 3단계 — 신뢰성과 이용조건의 증거 확인

| 축 | 확인할 내용 | 증거 |
|---|---|---|
| 정체성·책임성 | 실제 운영자, 공식 계정 연결, 저자·연락처·정정 경로 | 공식 소개·편집 정책·계정 연결 페이지 |
| 근거 추적 | 인용 원문, 데이터·논문·제품 발표 연결, 재전재 여부 | 표본의 주장과 원자료 대조 |
| 독립성·표시 | 광고·협찬·제휴·자사 홍보 구분, 동일 원자료 재인용 | 기사 표시, 소유·계열 관계 |
| 정확성 | 핵심 수치·날짜·버전·연구 결과의 일치, 정정·철회 반영 | 원자료 및 독립 근거의 비교 |
| 이용조건 | 자동 접근, API 조건, 저장·발췌·요약·표시 방식과 실제 동작의 정합성 | 공식 약관·라이선스·robots와 보관 정책 |

실행 시 공식 사이트·원자료를 직접 열어 최신 상태를 확인한다. robots 결과, 약관 URL의 존재, 시스템의 V1 통과를 별도 증거로 기록한다. 운영 정책의 자동 승인과 실제 이용조건 검토를 같은 것으로 취급하지 않는다. 해석이 필요한 항목은 근거와 쟁점을 남기고 확인 필요로 분류한다.

**산출물:** 발행자별 신뢰성 근거표, 채널별 이용조건 확인표. 동일 제공자의 공통 정책은 재사용하되 계정·콘텐츠별 예외를 확인한다.

### 4단계 — 콘텐츠 적합성과 수집 품질 측정

- 기본 관측 구간은 최근 30일, 운영 변동은 최근 7일과 비교한다. 저빈도 소스는 90일까지 확장하고 기간을 표시한다.
- 소스별 최근 10건과 기간 내 재현 가능한 무작위 10건, 총 최대 20개 고유 콘텐츠를 수동 검토한다. 부족하면 전건을 보고 표본 부족으로 표시한다.
- 문제 발생·판정 경계 소스는 최대 50건으로 확장한다. 동일 원문은 내용 검토를 재사용하되 채널별 중복 비용은 각각 계산한다.
- 표본의 10%와 중단·교체 제안 항목은 2차 검토한다. 이견과 수정 이유를 남긴다. 표본 결과를 전체 기간의 정확도로 단정하지 않는다.

| 지표 | 측정 방식 |
|---|---|
| 목적 적합성 | 원문을 수동 판정한 DX 관련 건수 / 검토 가능 표본 수. 자동 분류와 불일치율 병기 |
| 정보 가치 | 새로운 기술 변화·실증·표준·연구·제품 사실을 제공하는지, 단순 광고·반복 요약인지 |
| 최신성 | 실제 발행일, 수정일, 최초 수집일을 분리. 30일 초과 비율과 날짜 미확인 비율 표시 |
| 콘텐츠 유형 | 기사·논문·릴리스와 목록·태그·제품 DB·상시 문서를 구분. 참고자료 가치는 별도 인정 |
| 고유 기여 | 동일 원문·이슈 중복 제거 후 이 소스만 추가한 유효 정보 수. 단순 URL 차이를 고유 정보로 세지 않음 |
| 수집 품질 | 성공률, 429·403, 날짜·제목·원문 URL 누락, 잘못된 본문 추출, 지연 |
| 처리 효율 | 수집량·카드 시도량 대비 유효 고유 항목 수. 토큰·비용 기록이 없으면 시도량을 대리지표로 명시 |
| 최종 사용 | 브리핑·레이더 반영 건수와 근거 품질. 미발행 기간의 사용량 0을 출처 저품질로 해석하지 않음 |

**산출물:** 수집처별 측정표, 원문-수집 항목-한국어 카드 대조 표본, 수집·분류·요약 오류의 원인 구분.

### 5단계 — 포트폴리오 판정과 정리안

평가 결과는 신뢰성 `충분 / 제한적 / 미확인 / 중대한 문제`, 적합성 `핵심 / 보완 / 낮음 / 미확인`, 운영 품질 `양호 / 개선 필요 / 사용 곤란 / 미측정`으로 기록한다. 이용조건은 별도 확인 상태로 유지한다. 종합점수만으로 자동 삭제하지 않는다.

| 조치안 | 판단 기준 |
|---|---|
| 유지 | 근거가 확인되고 유효한 고유 정보를 안정적으로 제공 |
| 용도·범위 제한 | 탐색·참고 가치가 있으나 사실 근거로 부족하거나, 특정 카테고리만 유효 |
| 채널 개선·교체 | 발행자는 유용하지만 현재 피드·사이트맵·검색식의 잡음·오류가 큼 |
| 통합 | 같은 원문·쿼리의 반복이며 제거 후에도 고유 정보와 출처 추적을 유지 가능 |
| 중단 후보 | 중대한 근거 문제, 확인된 이용조건 충돌, 개선해도 고유 가치가 낮음 |
| 관찰·확인 보류 | 표본·기간·정체성·이용조건 증거가 부족하여 결론 불가 |

정리 전후의 기술·테마, 지역·언어, 4개 트랙, 공식·독립·커뮤니티·연구 비중을 비교한다. 수집처 수와 고유 유효 콘텐츠 수를 모두 본다. 현행 트랙 목표 100/100/35/25는 코드의 운영 설정이며 최적 구성으로 전제하지 않는다. 교체 후보는 실제 확인 후 제안한다.

**산출물:** 전체 판정대장, 우선 조치 목록, 커버리지 변화표, 수정 제안 diff. 항목별 사유·증거·예상 효과·재검토일을 붙인다.

### 6단계 — 후속 적용 및 관찰 계획

실제 변경을 진행할 때 카탈로그·DB 상태의 변경 전 스냅샷과 복원 방법을 준비하고 소규모 묶음부터 적용한다. 수집 채널 변경으로 V검증이 초기화되는 영향과 후보 소스의 카드·발행 노출 경로를 함께 확인한다.

적용 후 최소 7일간 유효 고유 항목, 중복·오래된 페이지, 처리량, 핵심 테마 누락을 비교한다. 저빈도 소스는 30~90일 동안 별도 관찰한다. 개선 성공은 처리량 감소뿐 아니라 필요한 기술 신호가 유지되는지로 판단한다. 구체 목표치는 1~4단계 기준선 확보 후 정한다.

## 4. 완료 기준과 실행 단위

- 사용자가 제시한 편중, 신뢰성·인지도, OSS 트렌드, SNS·인물, 업체 정보의 다섯 질문에 각각 현황·근거·공백·개선안을 제시한다.
- 카탈로그 등록, 실제 수집 성공, 분석·화면 제공 상태를 구분한다. 관측 기간이 부족한 추세는 보류한다.
- 카탈로그 전 항목과 DB 차이 항목에 판정 또는 보류 사유가 있다.
- 발행자 신뢰성, 채널 품질, 개별 주장 신뢰성을 혼동하지 않는다.
- 모든 유지·제한·통합·교체·중단 제안에 증거와 표본·관측 기간이 있다.
- 근거 없는 이용조건 승인, 데이터 부족에 의한 자동 탈락이 없다.
- 정리 전후의 고유 정보와 핵심 기술·지역 커버리지 변화가 설명된다.
- 실제 운영 변경 없이 검토 결과와 수정 제안만으로 먼저 검토 가능한 상태를 만든다.

첫 실행 묶음은 **전수 대장·단계별 편중 기준선 작성 + 우선 소스 30개 파일럿 평가 + OSS·SNS·업체 커버리지 예비표**로 한다. 파일럿에는 4개 트랙, 대량 사이트맵, 중복 검색식, 저빈도 전문 소스, 주요 인물 계정과 업체 공식 채널을 포함한다. 30개 표본으로 전체 편중을 추정하지 않고, 편중은 가능한 전체 운영 데이터로 계산한다. 항목당 검토 시간을 측정한 뒤 전체 소요를 산정한다. 전 항목을 최대 20건씩 검토하면 최대 25,460건이므로 단기간 전수 심층 완료를 약속하지 않는다.
